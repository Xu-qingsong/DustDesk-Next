# DustDesk 开发与发布规范

本文件是当前主线的开发、版本编号和 GitHub Release 说明规范。以后推送并发布项目时均遵循本文件；用户明确指定的版本或发布范围优先。

## 开发与验证

- 使用 Electron 主进程、类型化 preload API 和 React 渲染层；保留 `contextIsolation`、`sandbox`，禁用渲染层 `nodeIntegration`。
- 应用菜单按 `app.isPackaged` 区分：开发模式保留调试菜单，安装版和免安装绿色版移除顶部应用菜单，保留原生窗口标题栏和托盘菜单；不要仅用自动隐藏菜单，避免按 Alt 后重新出现。打包启动验证须检查菜单确实移除。
- 改动应包含必要的错误、加载和空状态；页面与桌面小组件共用数据来源，并验证双向同步。
- 剪贴板页面和小组件按需加载可见图片的缩略图，完整图片仅在打开预览时读取；预览不得写入系统剪贴板，复制仍使用原始图片。验证历史图片读取、缺失图片重试、文字换行、预览关闭与多窗口同步。
- 文本工具箱、图片工具箱和局域网传输菜单首次默认隐藏，可在设置的侧栏菜单中开启；保留已保存的显示选择（含全部显示），恢复默认时重新隐藏这三个入口。
- 主窗口、小组件、快速记录、截图与贴图入口按需加载，主窗口页面首次访问时加载；工具箱和截图页访问后保持草稿。主窗口便签标题与正文连续输入合并保存，退出前必须强制提交；失败保留待保存内容，验证覆盖重试、切页与退出。
- 初始读取及保存后重新读取工作区时，迟到的快照不能覆盖期间收到的更新广播；验证多窗口同步与延迟读取并发。
- 存在已收纳项目时，真正退出应用前询问“恢复并退出”“保留收纳并退出”或“取消”，默认聚焦取消；没有已收纳项目时直接退出，关闭主窗口驻留托盘时不询问。选择恢复时保留分类与撤销记录，下次启动重新收纳；恢复前持久化临时位置，同名项目另取名称且不覆盖。取消退出恢复编辑状态，恢复失败取消退出并提示，验证退出选择、重启、同名冲突和文件夹内容。
- 表单下拉选择、可搜索列表和日期／时间使用 `src/renderer/src/components/ui` 中的共用控件，沿用主题变量，不新增浏览器原生选择菜单或日期弹窗。日期采用本地日历值，时间使用 24 小时制；弹出控件先处理 Esc 和键盘焦点，再交还外层弹窗或截图编辑器。
- 颜色、复选框、开关、数字输入、滑块、进度和标签联想同样使用共用控件。数字允许暂时清空，失焦或 Enter 后提交并校验范围；颜色通过色板、HEX／RGB 设置。删除确认使用应用内弹窗，默认聚焦取消；禁止使用 `window.confirm`。控件须支持明暗主题、禁用状态、键盘和中文输入法。
- 数字输入尚未提交的草稿（包括暂时清空）不能被工作区后台同步覆盖；清空后失焦恢复最新已保存值，验证其他窗口同步与范围校验。
- 先执行 `npm run check:silent`，完成类型检查、单元测试、生产构建及无窗口界面回归。若测试被跳过，需要补验或在发布记录中说明。
- 再集中执行本次改动相关的真实 Electron 测试。发布前验证 Windows 打包产物可启动，且显示的版本号与发布版本一致。
- 不把本地工作区数据、账号凭据、测试截图、日志、构建目录或安装包提交到 Git。安装包通过 Release 附件分发。

新增工具箱与局域网模块的行为、数据位置和验证方法见 [工具箱与局域网传输](TOOLBOX.md)。局域网设备私钥和续传任务独立于工作区备份保存；涉及传输的改动必须验证双端中断与重启恢复，不能仅验证发送请求成功。

## 版本编号

- 应用版本使用 `MAJOR.MINOR.PATCH`，Git 标签使用 `vMAJOR.MINOR.PATCH`，Release 标题统一为 `DustDesk vMAJOR.MINOR.PATCH`。
- 用户未指定版本时，每次正式发布默认将补丁号加一，例如 `v1.0.0 → v1.0.1 → v1.0.2`；本项目口语中的“小版本递增”指补丁号递增。
- 发布前核对 `package.json`、Git 标签和本仓库最新正式 Release，使用三者中最高的正式版本作为递增基准，避免重复编号。已有标签或 Release 不得覆盖。
- 用户指定版本时使用指定版本；若该版本已发布，应说明冲突并选择新的版本，不能静默覆盖现有版本。
- 同步更新 `package.json`、`package-lock.json` 中的根包版本、README 的当前版本和本次版本说明。
- 可以使用 `npm version <版本号> --no-git-tag-version` 同步包版本；验证和打包完成后，再为最终发布提交创建同名标签。
- 仅推送开发代码不自动创建正式版本；用户要求“推送并打包发布版本”时，需完成代码推送、标签、Release 和附件上传。
- 用户明确要求调整当前已发布版本的附件时，可修订该版本附件和介绍，不递增应用版本、不移动既有标签；使用原发布代码的打包目录生成替代附件，打包策略与文档改动推送主分支。涉及应用代码改动时应发布新版本。

## 发布产物

- 默认只发布 Windows x64 NSIS 安装包 `DustDesk-X.Y.Z-x64.exe`、免安装绿色版 `DustDesk-X.Y.Z-x64-green.zip` 和 `SHA256SUMS.txt`。
- 绿色 ZIP 必须包含完整的 Electron 应用目录，解压后直接运行 `DustDesk.exe`，无需安装或运行自解压启动器；不能只打包单个 EXE。
- 绿色版数据继续保存在 `%AppData%\DustDesk.Next\Data`，与安装版使用相同的默认数据位置；移动或删除解压目录不会迁移或删除工作区。
- 不生成或上传 `*-portable.exe` 便携启动器。发布时精确选择当前版本文件，禁止使用通配符上传旧产物。
- 发布前将实际绿色 ZIP 解压至独立测试目录，验证主程序启动、版本显示、数据读取和小组件功能，再核对 ZIP 的 SHA-256。

## 版本介绍格式

版本说明保存在 `docs/releases/v<版本号>.md`，GitHub Release 正文使用同一份文件，确保仓库文档、发布页面和应用内更新提示一致。

参考用户指定的布局：采用 Markdown 二级标题，标题下按无序列表逐条介绍；不使用表格或嵌套列表，不增加装饰性图标。每个标题上方留空行，每条内容说明具体问题或功能以及用户可感知的结果。

章节顺序固定如下；无内容的可选章节直接省略，不保留空标题：

1. **Bug 修复**：列出实际修复的问题，说明触发场景和修复后的行为。
2. **新增功能**：列出本版本首次提供的功能，说明入口或用途。
3. **优化与调整**：可选，列出性能、布局和已有交互的改进。
4. **破坏性变更**：有不兼容的设置、数据格式、接口或行为变化时必须列出，同时提供升级或回退方法。
5. **已知问题**：可选，列出仍未解决、会影响用户使用的限制及可行的处理办法。
6. **下载与安装**：列出本版本安装包、免安装绿色 ZIP 及校验文件名称，说明平台及解压运行方式。

内容要求：

- 以“修复…”“新增…”“优化…”开头，避免仅写“修复若干问题”“优化体验”等无法核对的描述。
- 基于上一个正式版本与本次最终代码的实际差异编写；不要把既有功能、计划或未经验证的能力写成新增或已修复。
- 同一问题合并为一条，避免重复；涉及重要限制时明确写出，不承诺“彻底杜绝丢失”等无法证明的结果。
- 只有存在真实 Issue / PR 时才附仓库链接与编号，不虚构引用。
- 如数据格式升级，应明确说明升级前备份、旧版读取限制和回退方式；发现有未解决的重要问题时如实记录。
- GitHub Release 正文不混入开发过程、测试流水账或个人机器路径。验证结果记录到发布提交或开发记录中。

模板：

```markdown
## Bug 修复

- 修复【触发场景】下【具体问题】，现在【修复后行为】。

## 新增功能

- 新增【功能】，可在【入口】完成【用途】。

## 优化与调整

- 优化【已有功能或布局】，改善【可观察结果】。

## 破坏性变更

- 【变化、影响范围及升级／回退方法】。

## 已知问题

- 【当前限制及处理办法】。

## 下载与安装

- `DustDesk-X.Y.Z-x64.exe`：Windows 10/11 x64 安装包。
- `DustDesk-X.Y.Z-x64-green.zip`：Windows 10/11 x64 免安装绿色版，解压后运行 `DustDesk.exe`。
- `SHA256SUMS.txt`：以上文件的 SHA-256 校验值。
```

## 发布流程

1. 确认远程仓库为 `https://github.com/Xu-qingsong/DustDesk-Next`，核对最新正式版本、标签和当前工作区改动。
2. 按版本规则确定版本，同步包版本、README 和 `docs/releases/v<版本号>.md`。
3. 执行无窗口检查、相关真实窗口测试；失败必须修复后重试，不将跳过测试写成通过。
4. 执行 `npm run dist -- --publish never`，生成本版本 Windows x64 NSIS 安装包和免安装绿色 ZIP。打包时禁止工具自动发布旧目录中的文件。
5. 执行 `node tests/package-smoke.mjs` 和 `node tests/green-smoke.mjs` 验证打包后的应用与实际绿色 ZIP 解压后的程序启动、preload API、显示版本和小组件；测试使用独立数据目录。`DUSTDESK_PACKAGE_EXECUTABLE` 可指定其他解压后的应用主程序。为本版本安装包和绿色 ZIP 生成 `SHA256SUMS.txt`。只上传精确匹配本次版本的产物，不上传旧版本、便携启动器 EXE 或 `win-unpacked`。
6. 审核最终差异，提交代码、开发文档和版本说明，将发布提交推送到主分支。若远程分支有新提交，应先处理差异并重新验证，不强制覆盖远程历史。
7. 为同一提交创建并推送版本标签；创建草稿 Release，上传并核对附件。Release 正文直接读取已提交的版本说明文件。
8. 确认附件名称、大小及校验值正确后，将草稿设为正式 Release 和最新版本；核对发布页面、标签提交和下载链接。

默认产物和标签均对应同一最终提交。Windows 校验命令示例：

```powershell
Get-FileHash release/DustDesk-1.0.1-x64.exe -Algorithm SHA256
Get-FileHash release/DustDesk-1.0.1-x64-green.zip -Algorithm SHA256
```

开发设计的历史记录见 [Electron 重构计划](ELECTRON_REFACTOR_PLAN.md)；版本发布遵循本文的当前规则。
